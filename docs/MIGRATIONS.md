# Migrations: how to apply one to production without breaking the history

## What went wrong, so it is not repeated

On 2026-09-25 `prisma migrate reset` on a developer machine failed while seeding:

    invalid input value for enum "ChecklistItemType": "SITE_RULE"

The seed was fine. **The migration history could not build the schema the code
compiles against.** Two separate causes, both invisible until that moment:

1. **Objects with no migration at all.** Three enum types (`CppRevisionStatus`,
   `ArrangementKey`, `RiskTopic`), two enum values (`ChecklistItemType.SITE_RULE`,
   `DocumentCategory.DRAWING`), five tables (`CppRevision`, `CppRevisionEvent`,
   `StandardArrangement`, `SiteArrangement`, `SiteRiskTopic`) and three columns
   (`Worker.firstName`, `Worker.surname`, `Worker.cscsSchemeId`) existed in
   `schema.prisma` and in production, and in no migration. They were created by
   `prisma db push` locally and hand-run SQL in production.

2. **Migrations applied but never recorded.** Twelve migrations existed as files
   and had been applied to production with `psql -f` by one-off runner scripts.
   `psql` does not write to `_prisma_migrations`, so production reported 63 of 75
   migrations and `prisma migrate status` was a work of fiction.

Production was never broken. **Reproducibility was** — a new developer, a staging
instance, or a disaster-recovery rebuild all failed the same way. That is a fault
which stays invisible until the day it is urgent.

Repaired by `prisma/migrations/20260925160000_repair_migration_history`, which was
generated by `prisma migrate diff` rather than written by hand, and recorded in
production as applied rather than executed (production already had every object).

## The rule

**Every schema change gets a migration file, and production gets a recorded row.**

    npx prisma migrate dev --name what_it_adds     # never `db push` for a real change

`prisma db push` is for throwaway experiments on a local database only. The moment
a change is going to production, it needs a migration.

## Applying one to production

Production is Azure-only and needs a temporary firewall rule, so this happens from
a runner script. Either approach is fine, but **the recording step is not
optional**:

**Preferred — let Prisma do both:**

    DATABASE_URL="$PROD_URL" npx prisma migrate deploy

This applies what is outstanding and records it. Nothing else to remember.

**If you must run the SQL yourself** (a long backfill you want to watch, a
statement `migrate deploy` cannot express), record it immediately afterwards:

    psql "$PROD_URL" -X -v ON_ERROR_STOP=1 -f prisma/migrations/<name>/migration.sql
    DATABASE_URL="$PROD_URL" npx prisma migrate resolve --applied <name>

Forgetting the second line is exactly how twelve migrations went unrecorded.

**If production already has the objects** (a change applied out of band before this
rule existed), add the migration file and record it WITHOUT running it:

    DATABASE_URL="$PROD_URL" npx prisma migrate resolve --applied <name>

Check first that production really does match, with
`prisma migrate diff --from-url "$PROD_URL" --to-schema-datamodel prisma/schema.prisma`.

## The guard

`scripts/check_migration_drift.sh` builds the schema from the migration history
alone into a scratch database and diffs it against `schema.prisma`. Anything other
than empty is drift. It runs in the deploy gates, and takes about twenty seconds:

    bash scripts/check_migration_drift.sh

It catches cause (1) above. It does **not** catch cause (2), because it never looks
at production — for that, compare the row count in `_prisma_migrations` against the
number of directories in `prisma/migrations`, which `prisma migrate status` will
tell you in one line.

## One known, deliberate difference

Production carries four indexes and four `updatedAt` DEFAULTs that `schema.prisma`
does not declare, left over from hand-written migration SQL. They are redundant
rather than wrong, a rebuilt database will not have them, and removing them from
production is a change nobody has asked for. `prisma migrate diff` from production
to the schema will always show those eight statements; that is expected, and is not
the same thing as production missing something.

Note also that `@default(dbgenerated(...))` must be written with the text Postgres
normalises to — including `::text` casts and the extra parentheses — or the diff
reports a difference that no migration can ever resolve.
